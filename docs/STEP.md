# STEP.md — 最小单元开发流程

> **是什么：** 每一步开发的标准化流程。AI 和人类开发者共享同一套规则。
> **怎么用：** 每步开始前，把本文档作为 AI 的系统指令前缀。AI 按 5 个阶段执行，每阶段有明确的输入/输出。

---

## 流程总览

```
READ ──→ DESIGN ──→ CHECK-1 ──→ IMPLEMENT ──→ TEST ──→ CHECK-2 ──→ DONE
(读)      (设计)     (设计审批)    (实现)        (自动测试)  (人工验收)   (记录)
                        ↑                                      ↑
                   闸门 1: 未批准不写代码                    闸门 2: 未验收不标记完成
```

| 阶段 | 做什么 | 输出 |
|------|--------|------|
| **READ** | 读计划、读上一步 done、读现有代码 | 理解上下文 |
| **DESIGN** | 确认接口、检查前后兼容性、决定是否偏离 plan | 设计方案 |
| **CHECK-1** | AI 提交设计方案，人类审批 | 人类批准 ✓ |
| **IMPLEMENT** | 按 plan 创建/修改文件，先类型后实现 | 代码 |
| **TEST** | 跑自动化测试（TS 类型检查 + 单元测试 + 构建） | 测试结果 |
| **CHECK-2** | **人类亲自运行功能、手动验收，确认达到预期** | 人类验收 ✓ |
| **DONE** | 写 done 文档、更新索引 | `docs/done/step-NN.md` |

> **两个闸门都是强制的。** CHECK-1：人类未批准 → AI 不得写代码。CHECK-2：人类未亲自验收 → 步骤不得标记为 DONE。

---

## 1. READ（阅读阶段）

**目的：** AI 在动手前必须完整理解"我要做什么"和"已经有什么"。

### 必须读的文件（按顺序）

```
[1] docs/STEP.md                          ← 本文件（流程规则）
[2] docs/development-plan.md              ← 找到本步对应的章节
[3] docs/done/step-{NN-1}.md              ← 上一步的记录（了解最新状态）
[4] 本步将要修改的文件（Read 工具）         ← 确认现有代码不是假设的样子
```

### 读完后自问

- 本步的输入是什么？（类型、数据）
- 本步的输出是什么？（类型、文件）
- 依赖哪些已完成步骤？（它们真的完成了吗？）
- 本步完成后，下游哪个步骤会被解锁？

---

## 2. DESIGN（设计阶段）

**目的：** 在写代码之前，确认设计方案是合理的，不会破坏已完成的工作。

### 检查清单

```
□ 接口是否和 development-plan.md 中定义的一致？
  → 如果不一致：为什么变？记录到 done 里。

□ 是否修改了任何共享类型（Phase 0 定义的 Pydantic/TS 类型）？
  → 如果是：这是破坏性变更。必须先确认，然后更新所有引用。

□ 是否依赖了尚未实现的步骤？
  → 如果是：用 Mock 替代。Mock 数据从 plan 中取。

□ 是否修改了已完成步骤产出的文件？
  → 如果是：这是回溯修改。必须先确认，然后在 done 里记录原因。
```

### 修改规则

| 修改方向 | 规则 |
|----------|------|
| **向前修改（改未实现的步骤）** | ✅ 允许。直接在 plan 对应章节加注释说明变更。 |
| **向后修改（改已完成步骤的代码）** | ⚠️ 需要确认。改完后必须重跑那个步骤的测试。在 done 里标记 `BREAKING`。 |
| **修改共享类型（Phase 0）** | ⛔ 破坏性最大。必须团队确认。所有引用处都要更新。 |

---

## 3. CHECK-1（设计审批阶段）🔴 强制闸门

**目的：** AI 在写代码之前，必须把设计方案提交给人类审核。没有人类批准，不得进入 IMPLEMENT。

### AI 必须提交的内容

```
1. 本步要做什么（一句话）
2. 涉及哪些文件（新建、修改、删除），每个文件的操作和原因
3. 接口/类型变更（新增/修改了哪些共享类型？是否 BREAKING？）
4. 风险点（哪些已完成步骤会受影响？依赖什么？有什么不确定？）
```

### 人类响应

| 响应 | 含义 | AI 行为 |
|------|------|--------|
| "批准 / 开始 / 可以 / 没问题" | 方案通过 | 进入 IMPLEMENT |
| "等等，XXX 需要改" | 方案有缺陷 | AI 回到 DESIGN，调整方案后重新 CHECK-1 |
| "跳过这步 / 先不做" | 暂缓 | 在 done 里记录原因，标记 `⏭️` |
| 无响应 | 人类不在/思考中 | **AI 必须等待，不得自行进入 IMPLEMENT** |

### 通过的标志

AI 确认收到以下任一关键词后，才能进入 IMPLEMENT：

```
批准 | 开始 | 可以 | 没问题 | go | start | ok | proceed | yes | 👍
```

---

## 4. IMPLEMENT（实现阶段）

**目的：** 按 plan 写代码。先类型，后实现。Mock 先行。

### 实现顺序（强制）

```
1. 类型/接口定义（Pydantic model / TS interface）
2. Mock 数据（如果 plan 提供了）
3. 函数签名 + docstring（不写实现）
4. 核心逻辑
5. 边界情况处理（错误处理、超时、空值）
```

### 代码规范

- 每个文件不超过 300 行（超过就拆分）
- 每个函数不超过 50 行
- 所有 public 函数必须有 docstring（类型签名 + 一句话描述）
- 用 `loguru` 替代 `print`，关键节点打 log
- Comment 写"为什么"，不写"是什么"

### AI 实现时的要求

- **不要一次写 5 个文件。** 一个文件写完 → 确认正确 → 下一个。
- **不要猜测接口。** 接口定义在 plan 里，原样使用。如果 plan 没有，先问。
- **不要跳过错误处理。** 每个外部调用（LLM API、数据库、文件 I/O）都要 try/except。

---

## 5. TEST（测试阶段）

**目的：** 验证本步产出是否满足验收标准。

### 测试分层

```
Layer 1: 单元测试（Mock LLM / Mock DB）
  → pytest tests/test_xxx.py
  → 每个 public 函数至少 1 个 happy-path 测试

Layer 2: 集成测试（真 DB + Mock LLM）
  → 验证本步的模块能和其他已完成模块正确交互

Layer 3: 手动验证（真 LLM）
  → 只在需要验证 LLM 输出质量时使用
  → 比如 Persona 生成是否自然、叙事是否连贯
```

### 验收标准

从 development-plan.md 中复制本步的验收标准，逐条打勾。

### 测试失败怎么办

```
1. 确认是代码 bug 还是测试写错了
2. 修复 → 重跑 → 通过
3. 如果发现是设计问题（接口不匹配、plan 不合理）：
   → 回到 DESIGN 阶段重新设计
   → 在 done 里记录：为什么 plan 的设计行不通
```

---

## 6. CHECK-2（人工验收阶段）🔴 强制闸门

**目的：** 自动化测试不能替代人类判断。人类必须亲自运行功能、眼见为实，确认达到预期后才能标记 DONE。

### AI 的职责

AI 在 TEST 通过后，必须向人类提供：

```
1. 验收清单（从 plan 中复制本步的验收标准）
2. 测试结果摘要（自动化测试：多少通过、多少失败）
3. 如何手动验证的操作指南（启动命令、访问 URL、操作步骤）
4. 已知问题（本步未解决的事项）
```

### 人类的职责

人类必须亲自执行以下操作：

```
□ 启动后端（python run.py）→ /health 返回 200
□ 启动前端（npm run dev）→ 页面正常加载
□ 按操作指南手动走一遍核心交互
□ 确认输出符合预期（不是"看起来差不多就行"）
□ 确认没有明显的 UI 崩溃、报错、或数据不一致
```

### 人类响应

| 响应 | 含义 | AI 行为 |
|------|------|--------|
| "验收通过 / 没问题 / 可以标记 done" | 功能达到预期 | 进入 DONE，写 done 文档 |
| "XXX 有问题 / 不对" | 发现问题 | AI 回到 IMPLEMENT 修复，重新 TEST，再次 CHECK-2 |
| "不在电脑前 / 等会儿测" | 暂缓 | AI 等待，不得自行标记 DONE |

### AI 不得做的事

- ❌ 不得在人类验收之前写 done 文档
- ❌ 不得代替人类说"看起来没问题"
- ❌ 不得因为测试全绿就跳过 CHECK-2
- ❌ 不得催促人类"请尽快验收"

### 通过的标志

人类明确表示功能正常后，AI 才能进入 DONE。

---

## 7. DONE（记录阶段）

**目的：** 留下可追溯的开发记录。下一个人（或 AI）读了就知道这一步做了什么。

### 文件位置

```
docs/done/step-{NN}.md
```

NN 是两位数字序号（00, 01, 02...），和 development-plan.md 的步骤对应。

### 文件模板

```markdown
# Step {NN} — {步骤名称}

| 字段 | 值 |
|------|-----|
| 日期 | YYYY-MM-DD |
| Phase | {Phase X} |
| Plan 章节 | [development-plan.md](../development-plan.md) §{X.Y} |
| 状态 | ✅ done / 🚧 in-progress / ⚠️ blocked |

## 产出

| 文件 | 操作 | 说明 |
|------|------|------|
| backend/src/xxx.py | 新建 | ... |
| backend/src/yyy.py | 修改 | ... |

## 决策记录

（任何和 plan 不同的决定，以及原因）

- **决策 1：** 做了什么 + 为什么
- **决策 2：** ...

## 接口变更

（本步修改了哪些共享类型/接口？下游哪些步骤受影响？）

- 无 / （具体描述）
- ⚠️ BREAKING: 修改了 {类型名}，影响 Step {XX, YY}

## 测试结果

- [ ] 验收标准 1 — ✅ 通过
- [ ] 验收标准 2 — ✅ 通过
- [ ] 手动验证 — ✅ 通过

## 已知问题

（本步未解决、留给后续步骤处理的问题）

- 无 / （具体描述）

## 对下一步的提示

（下一步的开发者需要知道什么？）

- ...
```

### 写完后

1. 更新 `docs/done/README.md` 的索引表（追加一行）
2. 如果是 Phase 的最后一个步骤，标记 Phase 完成

## 6. 前端开发补充规则

> **何时适用：** Step 16–25（Phase 7 前端）。后端 Step 不读此节。

### 6.1 设计 Token 先行

任何页面组件**禁止使用裸 CSS 值**。必须使用 `tailwind.config.js` 中定义的 Token：

| 类别 | Token 示例 | 禁止 |
|------|-----------|------|
| 颜色 | `bg-bg-primary`, `text-accent-green` | `bg-[#0a0a0f]`, `text-[#00ff88]` |
| 字体 | `font-mono`, `font-sans` | `font-['JetBrains_Mono']` |
| 动画 | `animate-slide-in`, `animate-fade-in` | 内联 `@keyframes` |
| 间距 | Tailwind scale（`p-4`, `m-2`, `gap-6`） | 任意值 `p-[13px]` |

需要新 Token → 先在 `tailwind.config.js` 加，再在组件里用。

### 6.2 共享组件先于页面

新页面开始前，先检查能否拆出共享组件。Phase 7 标准共享组件：

| 组件 | 文件 | 用途 |
|------|------|------|
| `Card` | `components/shared/Card.tsx` | 玻璃面板容器 |
| `Badge` | `components/shared/Badge.tsx` | 状态标签 |
| `StatusDot` | `components/shared/StatusDot.tsx` | 呼吸指示灯 |
| `TerminalText` | `components/shared/TerminalText.tsx` | 等宽打字机文字 |
| `EmptyState` | `components/shared/EmptyState.tsx` | 🚧 建设中占位 |

页面独有逻辑放 `pages/`，跨页面复用的 UI 片断抽到 `components/`。

### 6.3 实现顺序（前端）

```
1. TS 类型定义（从 frontend/src/types/ 或 plan 取，严禁猜测）
2. Mock 数据（plan 提供了 MOCK_XXX 的，直接用）
3. 组件骨架（先写 HTML 结构 + Tailwind 类，不写状态逻辑）
4. 状态管理（Zustand store / useState / useReducer）
5. 交互逻辑（事件处理、API 调用、乐观更新）
6. 动画（最后加——结构不稳时加动画只会让调试更痛苦）
```

### 6.4 前端代码规范

- 每个 `.tsx` 文件不超过 300 行（超过就拆子组件）
- 每个组件函数不超过 200 行（React 组件天然比 Python 函数长）
- Props 必须显式声明 TypeScript 接口（不用 `any`）
- 用 Tailwind class 而非内联 `style={{}}`（除非值确实需要动态计算）
- 状态管理：组件内用 `useState`，跨页面用 `zustand` store，服务端缓存用 `@tanstack/react-query`
- 注释写"为什么"不写"是什么"（同后端规则）

### 6.5 测试 & 验收（前端）

```
Layer 1: 组件渲染（vitest + @testing-library/react）
  → 关键交互（按钮点击、表单提交）至少 1 个测试

Layer 2: Mock 模式独立运行
  → npm run dev → 不连后端也能浏览全部页面
  → 用 frontend/src/mocks/ 提供的 Mock 数据

Layer 3: 视觉走查（人眼）
  → 必须在浏览器中实际看到页面
  → 所有页面统一暗色主题
  → 动画无闪烁、无卡顿
  → 响应式不炸（至少 1280px 和 1920px 两档）
```

**前端 TEST 阶段 = 后端 TEST + 视觉走查。** 测试绿了不代表页面好看。

### 6.6 前端 DONE 模板（追加字段）

在 §7 的 DONE 模板基础上，前端 Step 的 done 文档追加：

```markdown
## 组件树

（本步新增/修改的组件层级关系，ASCII 树形）

## 视觉走查

- [ ] 暗色主题一致 — ✅
- [ ] 动画流畅 — ✅
- [ ] 1280px 不炸 — ✅
- [ ] Mock 模式可独立浏览 — ✅
```

【第二步：DESIGN】

【第七步：DONE】
按模板写 docs/done/step-{NN}.md，并更新索引。
