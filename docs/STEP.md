# STEP.md — 最小单元开发流程

> **是什么：** 每一步开发的标准化流程。AI 和人类开发者共享同一套规则。
> **怎么用：** 每步开始前，把本文档作为 AI 的系统指令前缀。AI 按 5 个阶段执行，每阶段有明确的输入/输出。

---

## 流程总览

```
READ ──→ DESIGN ──→ IMPLEMENT ──→ TEST ──→ DONE
(读)      (设计)      (实现)        (测试)     (记录)
```

| 阶段 | 做什么 | 输出 |
|------|--------|------|
| **READ** | 读计划、读上一步 done、读现有代码 | 理解上下文 |
| **DESIGN** | 确认接口、检查前后兼容性、决定是否偏离 plan | 设计确认（口头/注释） |
| **IMPLEMENT** | 按 plan 创建/修改文件，先类型后实现 | 代码 |
| **TEST** | 跑验收标准、手动验证 | 测试结果 |
| **DONE** | 写 done 文档、更新索引 | `docs/done/step-NN.md` |

---

## 1. READ（阅读阶段）

**目的：** AI 在动手前必须完整理解"我要做什么"和"已经有什么"。

### 必须读的文件（按顺序）

```
[1] docs/STEP.md                          ← 本文件（流程规则）
[2] docs/development-plan.md              ← 找到本步对应的章节
[3] docs/done/step-{NN-1}.md              ← 上一步的记录（了解最新状态）
[4] 本步将要修改的文件（Read 工具）         ← 确认现有代码不是假设的样子
```

### 读完后自问

- 本步的输入是什么？（类型、数据）
- 本步的输出是什么？（类型、文件）
- 依赖哪些已完成步骤？（它们真的完成了吗？）
- 本步完成后，下游哪个步骤会被解锁？

---

## 2. DESIGN（设计阶段）

**目的：** 在写代码之前，确认设计方案是合理的，不会破坏已完成的工作。

### 检查清单

```
□ 接口是否和 development-plan.md 中定义的一致？
  → 如果不一致：为什么变？记录到 done 里。

□ 是否修改了任何共享类型（Phase 0 定义的 Pydantic/TS 类型）？
  → 如果是：这是破坏性变更。必须先确认，然后更新所有引用。

□ 是否依赖了尚未实现的步骤？
  → 如果是：用 Mock 替代。Mock 数据从 plan 中取。

□ 是否修改了已完成步骤产出的文件？
  → 如果是：这是回溯修改。必须先确认，然后在 done 里记录原因。
```

### 修改规则

| 修改方向 | 规则 |
|----------|------|
| **向前修改（改未实现的步骤）** | ✅ 允许。直接在 plan 对应章节加注释说明变更。 |
| **向后修改（改已完成步骤的代码）** | ⚠️ 需要确认。改完后必须重跑那个步骤的测试。在 done 里标记 `BREAKING`。 |
| **修改共享类型（Phase 0）** | ⛔ 破坏性最大。必须团队确认。所有引用处都要更新。 |

---

## 3. IMPLEMENT（实现阶段）

**目的：** 按 plan 写代码。先类型，后实现。Mock 先行。

### 实现顺序（强制）

```
1. 类型/接口定义（Pydantic model / TS interface）
2. Mock 数据（如果 plan 提供了）
3. 函数签名 + docstring（不写实现）
4. 核心逻辑
5. 边界情况处理（错误处理、超时、空值）
```

### 代码规范

- 每个文件不超过 300 行（超过就拆分）
- 每个函数不超过 50 行
- 所有 public 函数必须有 docstring（类型签名 + 一句话描述）
- 用 `loguru` 替代 `print`，关键节点打 log
- Comment 写"为什么"，不写"是什么"

### AI 实现时的要求

- **不要一次写 5 个文件。** 一个文件写完 → 确认正确 → 下一个。
- **不要猜测接口。** 接口定义在 plan 里，原样使用。如果 plan 没有，先问。
- **不要跳过错误处理。** 每个外部调用（LLM API、数据库、文件 I/O）都要 try/except。

---

## 4. TEST（测试阶段）

**目的：** 验证本步产出是否满足验收标准。

### 测试分层

```
Layer 1: 单元测试（Mock LLM / Mock DB）
  → pytest tests/test_xxx.py
  → 每个 public 函数至少 1 个 happy-path 测试

Layer 2: 集成测试（真 DB + Mock LLM）
  → 验证本步的模块能和其他已完成模块正确交互

Layer 3: 手动验证（真 LLM）
  → 只在需要验证 LLM 输出质量时使用
  → 比如 Persona 生成是否自然、叙事是否连贯
```

### 验收标准

从 development-plan.md 中复制本步的验收标准，逐条打勾。

### 测试失败怎么办

```
1. 确认是代码 bug 还是测试写错了
2. 修复 → 重跑 → 通过
3. 如果发现是设计问题（接口不匹配、plan 不合理）：
   → 回到 DESIGN 阶段重新设计
   → 在 done 里记录：为什么 plan 的设计行不通
```

---

## 5. DONE（记录阶段）

**目的：** 留下可追溯的开发记录。下一个人（或 AI）读了就知道这一步做了什么。

### 文件位置

```
docs/done/step-{NN}.md
```

NN 是两位数字序号（00, 01, 02...），和 development-plan.md 的步骤对应。

### 文件模板

```markdown
# Step {NN} — {步骤名称}

| 字段 | 值 |
|------|-----|
| 日期 | YYYY-MM-DD |
| Phase | {Phase X} |
| Plan 章节 | [development-plan.md](../development-plan.md) §{X.Y} |
| 状态 | ✅ done / 🚧 in-progress / ⚠️ blocked |

## 产出

| 文件 | 操作 | 说明 |
|------|------|------|
| backend/src/xxx.py | 新建 | ... |
| backend/src/yyy.py | 修改 | ... |

## 决策记录

（任何和 plan 不同的决定，以及原因）

- **决策 1：** 做了什么 + 为什么
- **决策 2：** ...

## 接口变更

（本步修改了哪些共享类型/接口？下游哪些步骤受影响？）

- 无 / （具体描述）
- ⚠️ BREAKING: 修改了 {类型名}，影响 Step {XX, YY}

## 测试结果

- [ ] 验收标准 1 — ✅ 通过
- [ ] 验收标准 2 — ✅ 通过
- [ ] 手动验证 — ✅ 通过

## 已知问题

（本步未解决、留给后续步骤处理的问题）

- 无 / （具体描述）

## 对下一步的提示

（下一步的开发者需要知道什么？）

- ...
```

### 写完后

1. 更新 `docs/done/README.md` 的索引表（追加一行）
2. 如果是 Phase 的最后一个步骤，标记 Phase 完成

## 附录：AI Session 模板

每步开始时的 AI prompt 结构：

```
【角色】你是本项目的开发 AI。请严格遵循 docs/STEP.md 的流程。

【第一步：READ】
请阅读以下文件并按顺序理解：
1. docs/STEP.md（流程规则）
2. docs/development-plan.md 中关于 Step {NN} 的章节
3. docs/done/step-{NN-1}.md（上一步记录）
4. 本步涉及的全部现有代码文件

【第二步：DESIGN】
确认接口设计后向我汇报。如果有偏离 plan 的地方，必须先得到我的确认。

【第三步：IMPLEMENT】
按 plan 中的文件路径和接口实现。先类型后实现。

【第四步：TEST】
按 plan 中的验收标准逐条测试。

【第五步：DONE】
按模板写 docs/done/step-{NN}.md，并更新索引。

开始。
```
