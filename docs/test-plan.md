# Life Lab 模块级测试计划

> **适用范围：** M1-M12 的完整功能验收、Bug 修复和回归测试。
>
> **与开发流程的关系：** [STEP.md](STEP.md) 负责单个开发 Step；本文负责跨 Step 的完整模块验收。开发 Step 标记 DONE，不代表对应模块已经通过本文规定的模块级测试。

---

## 1. 核心原则

1. **机器测试不能替代人工测试。** 单元测试、集成测试、构建全部通过，只能证明可进入人工测试，不能直接标记模块完成。
2. **按计划功能建立测试基线。** 不能只测试当前页面上看得见的内容；未实现、未接通或被隐藏的计划功能也必须被识别并记录。
3. **所有用户操作都在测试范围内。** 包括创建、编辑、复制、删除、启动、暂停、继续、停止、取消、重置、导入、导出、刷新和重启恢复等细节。
4. **Bug 一个一个修、一个一个测。** 只有确认属于同一根因时，才允许合并处理多个 Bug。
5. **人工未确认，不得 DONE。** AI 不得用“测试全绿”“接口存在”或“页面能打开”代替人的实际操作验收。
6. **结果必须可追溯。** 测试环境、commit、命令、用例、实际结果、Bug 和遗留问题都要写入记录。
7. **基础架构改动必须全组确认。** 未获得确认前，测试过程不得擅自修改共享类型、公共接口、数据库结构或核心运行架构。

## 2. 文档与状态

| 文件 | 用途 |
|------|------|
| `docs/test-plan.md` | 测试流程、规则、模板和完成标准 |
| `docs/test-done/README.md` | M1-M12 测试状态索引 |
| `docs/test-done/mNN.md` | 单个模块的详细测试与验收记录 |
| `docs/bugs.md` | Bug 描述、状态、修复和回归记录 |

测试状态沿用开发记录的图例：

| 状态 | 含义 | 使用规则 |
|------|------|----------|
| ⬜ | 未开始 | 尚未进入模块级 READ，所有模块初始为此状态 |
| 🚧 | 进行中 | 已进入 READ、DESIGN、TEST、DEBUG、RETEST 或人工验收 |
| ✅ | 已完成 | 机器测试、完整手测、Bug 回归、人工确认和 DONE 文档全部完成 |
| ⚠️ | 受阻/有已知问题 | 存在阻断项或已知缺陷，不得视为完成 |
| 🔄 | 需要回溯修改 | 已测试模块因 Bug、接口或依赖变化需要修改并重测 |
| 🔀 | 此模块被后续步骤修改过 | 等待影响评估；评估后必须转为 🔄 或恢复为 ✅ 并追加记录 |

`🔀` 是临时状态，不是完成状态。后续改动影响功能、接口、数据或用户流程时转为 `🔄`；确认无影响时，必须在原测试记录中追加影响评估和验证证据后才能恢复 `✅`。

## 3. 标准流程

```text
READ
  -> DESIGN
  -> MACHINE TEST
  -> MANUAL TEST
  -> DEBUG <-> RETEST
  -> HUMAN ACCEPTANCE
  -> DONE
```

- 没有发现 Bug 时，可以跳过 DEBUG，但不能跳过 MANUAL TEST 和 HUMAN ACCEPTANCE。
- 发现设计、接口或计划冲突时，必须返回 DESIGN，不得边猜边改。
- 任一阶段受阻时，状态改为 `⚠️` 并记录原因、影响和解除条件。

## 4. READ：建立真实功能基线

### 4.1 必读内容

测试 Mx 前，AI 必须按顺序阅读：

1. `docs/test-plan.md`
2. `docs/STEP.md`
3. `docs/agent-lab-blueprint.md` 中 Mx 的模块定义、优先级和相关架构章节
4. `docs/development-plan.md` 中实现 Mx 的 Phase、Step、接口、Mock 和验收标准
5. `docs/plan-state2.md` 至当前最新 State Plan 中所有修改或增强 Mx 的章节
6. `docs/done/README.md` 以及所有实现、测试或回溯修改 Mx 的 `step-*.md`
7. `docs/bugs.md` 中所有涉及 Mx、其依赖和共享基础设施的问题
8. 根目录 `README.md`、使用教程、演示脚本和该模块的用户说明
9. Mx 涉及的前后端代码、路由、API、共享类型、数据库模型、Mock 和现有测试
10. 已完成的上游模块测试记录，以及上次测试后影响 Mx 的提交或文件变化

不能只读最初的 development plan。State Plan、DONE、Bug 记录和当前代码共同决定模块的现状；发现它们不一致时必须列出差异并请求确认，不能自行选择一个版本当作真相。

### 4.2 READ 输出

READ 完成后，AI 必须汇报：

- 计划要求的完整功能清单
- 当前代码实际实现的功能清单
- 缺失、占位、隐藏、降级或文档不一致的功能
- 输入、输出、数据持久化方式和外部依赖
- 上游依赖、下游消费者和模块内部状态顺序
- Mock、真数据库、真 LLM、网络、文件系统等环境要求
- 历史 Bug 和必须执行的回归用例
- 可能触及共享类型、公共 API、数据库或核心架构的风险

未形成上述基线，不得进入 DESIGN。

## 5. 测试依赖与并行规则

测试不是全部串行，也不是全部独立。

### 5.1 可以并行的内容

- 不依赖其他模块真实数据的单元测试
- 使用已确认 Mock 的页面和组件测试
- 功能盘点、用例设计和视觉检查准备
- 上游契约已冻结后的局部功能测试

### 5.2 必须按依赖执行的内容

- 真数据库、真实 API 和真实 LLM 集成测试
- 使用上游模块产出数据的功能
- 跨页面、跨模块和端到端用户流程
- 需要验证持久化、恢复、归档、评测或文件产出的流程
- 模块最终人工验收

DESIGN 必须根据当前代码和文档画出本模块的实际依赖，不允许凭模块编号猜测。上游模块尚未通过时，可以用 Mock 完成局部测试，但不得宣称下游端到端验收完成。

### 5.3 状态流程也有先后关系

暂停、继续和删除等功能必须放在完整状态链中测试，例如：

```text
创建 -> 启动 -> 确认运行 -> 暂停 -> 确认停止变化
     -> 刷新检查状态 -> 继续 -> 确认从原进度恢复
     -> 完成/停止 -> 删除 -> 刷新确认数据消失
```

只验证按钮可点击，不代表对应功能通过。

## 6. DESIGN：制定完整测试方案

DESIGN 必须从 READ 的功能基线生成测试矩阵，不得照搬已有自动化测试名称。

### 6.1 强制覆盖维度

| 维度 | 最低要求 |
|------|----------|
| 主流程 | 从用户入口到结果产出的完整 happy path |
| 控件 | 所有按钮、菜单、输入框、开关、标签页、快捷键和图标操作 |
| 数据生命周期 | 创建、读取、修改、复制、删除、持久化和清理 |
| 运行状态 | 未开始、加载、运行、暂停、继续、完成、失败、取消、重试、重置 |
| 边界与错误 | 空值、非法值、极值、重复提交、快速连续点击、超时、断网、后端或 LLM 失败 |
| 恢复能力 | 刷新、关闭重开、前后端重启、连接恢复和中断后的状态一致性 |
| 模式 | Mock、真数据库、真 LLM；不适用时说明理由 |
| 集成 | API 契约、共享类型、上下游模块和跨页面用户流程 |
| 前端体验 | 1280px、1920px、窄窗口、滚动、遮挡、溢出、加载、空态、禁用态、错误反馈 |
| 媒体与文件 | 动画、声音、下载、导入、导出、文件名、文件内容和清理 |
| 回归 | 历史 Bug、后续改动影响点和本轮修复关联功能 |

### 6.2 用例必填字段

每个用例必须包含：

1. 用例编号和功能名称
2. 测试层级：单元、集成、端到端或人工
3. 前置条件和依赖状态
4. 测试数据、运行模式和环境
5. 逐步操作
6. 每一步的精确预期结果
7. 需要检查的界面、数据库、日志、文件、声音或动画
8. 清理和恢复方式
9. 是否为阻断验收的强制用例

“功能正常”“页面没问题”“结果差不多”不是有效预期结果。

### 6.3 DESIGN 输出

AI 必须先向人汇报：

- 测试范围和明确不测的内容
- 依赖关系和执行顺序
- 机器测试清单
- 人工测试清单
- 测试数据与清理方案
- 风险、成本和真 LLM 调用计划
- 可能需要修改的基础架构或共享接口

涉及基础架构的方案必须先获得全组确认。没有确认，只能继续测试和记录，不能修改对应代码。

## 7. MACHINE TEST：机器测试

机器测试至少按以下层级执行：

1. **单元测试：** Mock LLM / Mock 外部服务；每个 public 函数至少有 1 个 happy-path 测试，并覆盖关键状态转换和边界条件。
2. **集成测试：** 真数据库 + Mock LLM；验证 API、持久化和已完成模块间交互。
3. **前端测试：** 组件渲染、关键交互、状态变化、错误反馈和必要的端到端自动化。
4. **静态检查与构建：** TypeScript、生产构建以及项目已有的质量命令。
5. **真 LLM 检查：** 仅用于必须验证输出质量的场景，不替代确定性的自动化测试；记录模型、参数、次数和费用风险。

测试结果必须记录实际命令、通过数、失败数、跳过数、警告和失败归属。不得只写“全部通过”。

机器测试失败时，先判断是生产代码、测试代码、环境还是既有问题；不得通过删除断言、扩大 Mock 或跳过测试制造通过结果。

---

## 8. MANUAL TEST：强制人工测试

### 8.1 强制规则

进入人工测试前，AI 必须根据本模块功能清单制定完整、可执行的手测步骤。未提供手测步骤、未由人工实际执行，或未逐项确认结果的模块，不得标记为完成。

AI 提供的手测指南必须包含：

- 环境启动和页面入口
- 测试账号、Agent、世界、任务或其他数据准备
- 每次只做一个动作的编号步骤
- 每一步对应的预期界面和数据变化
- 暂停、继续、停止、取消、重置、删除等状态细节
- 刷新、重启、超时、失败和恢复场景
- 宽屏、窄屏、滚动、遮挡和文本适配
- 下载文件、声音、动画和真实 LLM 输出的观察方法
- 失败时需要保留的截图、日志和复现信息
- 测试后的数据清理方法

人工测试人必须逐项报告 `通过 / 失败 / 受阻`。AI 可以协助浏览器检查，但不能代替人的最终体验判断和确认。

### 8.2 人工测试证据

至少记录：

- 测试人和日期
- commit
- 操作系统、浏览器和视口
- Mock / 真实模式、后端和 LLM 配置是否启用
- 用例实际结果
- 必要的截图、视频、日志或下载文件
- 人工验收结论

## 9. DEBUG 与 RETEST：逐项闭环

用户报告问题后，按以下顺序处理：

1. 在 `docs/bugs.md` 登记 Bug 编号、模块、严重级别、环境、复现步骤、预期与实际结果。
2. 使用同样的数据和步骤稳定复现；不能复现时继续收集证据，不猜测修改。
3. 定位根因并提出最小修复方案，说明涉及文件、回归范围和是否影响基础架构。
4. 人确认方案后，一次只修一个 Bug；同一根因的多个现象可合并，但必须逐项验证。
5. 先执行聚焦机器测试，再执行相关模块回归。
6. AI 向人工测试人提供该 Bug 的现场复测步骤。
7. 人工按原复现步骤和修复后路径确认通过，才能关闭 Bug。
8. 更新 `docs/bugs.md` 和当前模块测试记录。

人工复测失败时继续 `DEBUG <-> RETEST`，不得跳到 DONE。

## 10. 基础架构变更闸门

测试或修复涉及以下内容时，必须暂停并获得全组确认：

- Phase 0 共享 Pydantic / TypeScript 类型
- 公共 API 路径、请求、响应或 SSE 事件协议
- 数据库 Schema、迁移和已有数据兼容
- Agent、World、Team、Worker、Pipeline 等核心引擎架构
- 全局状态管理、路由、认证、持久化和恢复机制
- 依赖包、锁文件、构建或部署方式
- 已完成步骤的公共产出或跨模块契约

提案必须说明：修改原因、替代方案、是否 BREAKING、受影响模块、兼容方式、数据处理和必须重跑的测试。

未经确认不得修改。确认修改后：

1. 受影响模块先标记 `🔀`。
2. 完成影响评估后转为 `🔄` 或追加验证并恢复 `✅`。
3. 所有受影响的聚焦测试、集成测试和人工流程必须重跑。

## 11. HUMAN ACCEPTANCE 与 DONE

### 11.1 完成门槛

模块只有同时满足以下条件才能标记 `✅`：

- 计划功能全部进入测试清单，缺失功能已明确处理
- 强制机器测试通过
- 强制人工用例逐项通过
- 历史 Bug 和本轮 Bug 已完成必要回归
- 没有未处理的 P0 / P1 问题
- P2 / P3、限制和 wontfix 有明确理由、影响和后续安排
- 上下游依赖和端到端流程已验证
- 人工测试人明确确认验收通过
- 已创建 `docs/test-done/mNN.md` 并更新索引

“大部分功能正常”或“只剩小问题”不能标记为 `✅`，应使用 `⚠️` 并如实记录。

## 12. 自动触发复测

模块标记 `✅` 后，出现以下变化必须重新评估：

- 模块自身生产代码变化
- 共享类型、API、数据库或核心依赖变化
- 上游模块的数据、状态或行为变化
- 历史 Bug 复现或相似问题出现
- Mock 与真实环境行为不一致
- 浏览器、LLM 模型、关键依赖或部署环境发生重大变化

仅修改无关文档、注释或已证明不影响运行的内容，可以在测试记录中追加影响评估后保持 `✅`；其他情况不得静默保留完成状态。

## 13. AI 测试会话模板

```text
【角色】你是本项目的测试 AI。请严格遵循 docs/test-plan.md。

【READ】
完整阅读 test-plan、STEP、蓝图与 development plan 中 M{NN} 的章节、
所有后续 State Plan 增强、相关 DONE、bugs、用户文档、生产代码、Mock、测试和上游记录。
输出计划功能、实际功能、差异、依赖、历史 Bug 和环境要求。

【DESIGN】
制定覆盖全部功能、控件、状态、边界、错误、恢复、持久化、集成和视觉的测试矩阵。
先汇报机器测试方案和详细手测方案，不得直接宣布测试完成。

【TEST】
执行机器测试并记录真实命令和结果。随后提供逐步手测指南，等待人工逐项执行。

【DEBUG / RETEST】
发现一个问题，登记一个、定位一个、提出最小方案、确认后修改一个；
执行聚焦测试和回归，再提供现场人工复测步骤。未人工确认不得关闭。

【DONE】
只有全部强制用例和人工验收通过后，才能写 docs/test-done/m{NN}.md 并更新索引。
涉及共享类型、公共 API、数据库或基础架构时，必须先获得全组确认。
```
